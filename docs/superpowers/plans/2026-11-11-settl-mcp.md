# Plan: MCP that agents can use without guessing

Approved by the user on 2026-11-11. Spec: `docs/superpowers/specs/2026-11-11-settl-mcp-design.md`. Step 0 (committing the Nov 10 work) was declined; this slice builds on the uncommitted tree.

## Context
The sandbox and SDK slice (Nov 10, uncommitted) made Settl easy to try. The hosted MCP is now the weakest part for developers:
- `settl_list_services` returns only name, price and mode, so an agent has to guess what `input` to send. Per-call billing charges even when the provider rejects bad input.
- Every failure becomes `TOOL_FAILED`, which hides the real reason (`BrokerError.code`) and gives no next step.
- `settl_call` leaks internal `effects`, and nothing declares an output shape.
- Approvals can only be polled. `settl_get_budget` does a live chain read every call.
- Nothing lets an agent or directory discover the gateway, and connecting a client means reading docs.

You chose all four parts: service metadata, typed per-service tools, better errors/approvals/budget, and discovery plus a dashboard Connect panel.

## What exploration established
- **MCP SDK 2.4.0 capabilities:**
  - The server factory can be async and runs per request, so tools can be built from the DB catalog.
  - `fromJsonSchema()` turns a provider's raw JSON Schema into an input schema. It uses Ajv, throws eagerly on a bad schema, and the root must be an object.
  - `outputSchema` requires matching `structuredContent` on every non-error result.
  - Resources and prompts work stateless.
- **What doesn't work in this server's mode:** elicitation and list-changed notifications are unavailable in the `legacy: 'stateless'` mode the route uses, so approvals keep a polling fallback. The SDK has no server-card support, so the card will be a hand-written route.
- **Additive design keeps every consumer working:** keeping the six `settl_*` tools and the `error` string field preserves `apps/agent`, `packages/client`, `scripts/demo-e2e.ts` and roughly 10 test files. Only a few exact-equality assertions need updating (tool-name lists, `settl_list_services` and error `toEqual`s).
- **No checked-in migrations:** schema changes ship as a hand-written idempotent SQL file. The precedent is `apps/web/prisma/performance-upgrade.sql`, applied with `prisma db execute`.
- **Reusable pieces:**
  - `createBalanceService` in `lib/server/balances.ts` (15 s snapshot, in-flight coalescing, never throws). It only needs a seam so it honors the sandbox chain.
  - `BrokerError` codes are static strings, so they are safe to expose.

## Part A: Service metadata
- **Schema:**
  - `Endpoint` in `apps/web/prisma/schema.prisma` gains `description String?`, `inputSchema Json? @map("input_schema")` and `example Json?`.
  - New `apps/web/prisma/endpoint-metadata-upgrade.sql` uses `ADD COLUMN IF NOT EXISTS` in a transaction.
  - Update the README in `apps/web/prisma`.
  - Regenerate `packages/dev/src/schema.sql` (`npm run schema -w @settl/dev`).
- **Validation:** new `lib/server/service-metadata.ts` handles:
  - Description: at most 500 characters.
  - Input schema: an object-rooted JSON Schema, at most 16 KB, that compiles with `fromJsonSchema`.
  - Example: at most 4 KB, and it must validate against the schema when both are given.
  - One function shared by both registration paths.
- **Registration:**
  - `lib/server/handlers/register.ts` accepts and stores the three optional fields on create, and adds them to `drift`. It still never mutates an existing endpoint.
  - The dashboard create route `app/api/provider/endpoints/route.ts` accepts them too. `components/provider/endpoint-tools.tsx` `AddRouteForm` gets a description field plus optional JSON fields with inline errors.
- **SDK:** `RegisterOptions` in `packages/sdk/src/core.ts` gains `description?`, `inputSchema?` and `example?`. They are omitted from the body when undefined, so existing body assertions stay green.
- **Seed:** `prisma/seed.ts` adds metadata for the three demo services, filling only null columns. The sandbox picks it up automatically.
- **MCP:** `settl_list_services` returns `description`, `inputSchema` and `example`. `lib/server/dashboard.ts` selects the new columns where shown.
- **Broker:** if an endpoint has an `inputSchema`, `executeCall` validates `input` before quoting or paying. Invalid input returns `declined / invalid_input` with no charge. This protects per-call agents from paying for a rejected call. The check sits before the existing nonce/lock work, and existing broker tests stay unchanged.

## Part B: Typed per-service tools
- `createAgentMcpServer` in `lib/server/mcp-tools.ts` becomes async. `app/mcp/route.ts` awaits it.
- **Catalog cache:** new `lib/server/service-catalog.ts` caches active endpoints with metadata for 30 s per process. The register handler invalidates it in-process.
- **Tool names:** `slug(provider)_slug(name)`, lowercase `[a-z0-9_]`, at most 64 characters. Collisions get a short id suffix, and names never start with `settl_`.
- **Tool input:** `{ input, maxPricePhp?, approvalId? }`, where `input` is the service's own schema (any JSON when it has none).
- **Description:** the provider description plus the price and approval guidance. Annotations are `destructiveHint` and `openWorldHint`.
- **Behavior:**
  - Each tool runs the same `executeCall` path as `settl_call` through one shared function.
  - A service whose schema fails to compile is skipped and logged, never breaking the list.
  - Dynamic tools are capped at 40; beyond that, agents use `settl_call`.

## Part C: Errors, output, approvals, budget
- **Errors:** new `lib/server/mcp-errors.ts` maps public codes to `{ message, next, retryable }`.
  - It covers every `BrokerError` code, the tool codes and the `CallResult` reasons, for example `over_max_price` maps to "raise maxPricePhp or pick a cheaper service".
  - `safely()` returns `{ error: code, message, next, retryable }` for `BrokerError` instances only. Any other throw stays redacted as `TOOL_FAILED`, as the existing test requires.
  - The `error` field stays a string, so the existing decoders keep working.
- **Typed output:** `settl_call` and the dynamic tools declare a status-discriminated `outputSchema`. Results drop `effects` and gain a `next` hint on non-paid statuses.
- **`settl_wait_for_approval { approvalId, timeoutSeconds 1-55, default 25 }`:** read-only. It checks the approval once a second server-side and returns as soon as it is decided, staying under the 300 s function limit.
- **Budget:** `settl_get_budget` uses `createBalanceService`, keyed by agent, with the chain read through `readBalance`, so the sandbox still works. It adds `balanceAsOf` and `balanceSource`. Authorization never uses this cache (unchanged).
- **Clients:**
  - `packages/client`: `SettlToolError` gains `message`, `next` and `retryable`.
  - `callAndWait` uses `settl_wait_for_approval` and falls back to polling `settl_check_approval` on older gateways.
  - `settlTools` adds the new tool, for seven tools.
  - `ServiceInfo` adds the metadata fields.
  - `apps/agent` needs no change.

## Part D: Discovery and Connect panel
- **`app/llms.txt/route.ts`:** plain text covering what Settl is, the MCP URL, auth, the tools and the buy flow, generated from the same tool descriptions so it can't drift.
- **`app/.well-known/mcp/server-card.json/route.ts`:** before writing it, check the current MCP server-card proposal for the exact path and fields. If no stable spec exists, ship it under the proposal's path and say so in the docs. `proxy.ts` already leaves these paths public.
- **MCP resources and prompt:** `settl://services` (the catalog) and `settl://guide` (how to buy safely), plus a `buy_service` prompt.
- **Connect panel:** new `components/buyer/connect-agent.tsx` with tabs for Claude Code, Codex, Cursor and `@settl/client`, and a copy button.
  - On the new-agent success screen in `new-agent-form.tsx`, it fills in the once-shown key.
  - On `app/buyer/agents/[id]/page.tsx`, it shows a placeholder, because only the key's hash is stored.
  - It uses the gateway origin.

## Risks and operations
